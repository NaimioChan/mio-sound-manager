# 调研 TODO：任意音频文件的低延迟冷加载

状态：**未开始**。本文件是交给调研对话的工作清单。目标是把"点一个从未播放过的任意格式音频文件 → 出声"这条路径的延迟压到可接受范围，并确定后端架构。

前置阅读：`docs/research-notes-playback.md`（参考机已测数字）。那里的数据说明了两件事：解码很快（1–6ms 对常见素材），瓶颈在输出设备的周期（WASAPI 共享 10.1ms 固定）。所以调研的重点不是"怎么解码更快"，而是**如何在冷文件上同时避免解码等待和设备周期等待**。

## 约束与边界

- **不用 Web Audio**。`decodeAudioData` + `AudioBufferSourceNode` 这条 webview 内路径已被排除：它把播放锁在 Chromium 的音频线程和 `AudioContext` 时钟上，无法利用 ASIO，也无法控制设备周期。
- **UI/UX 已定**。Slip Sound 的交互模型是参考基准（列表为主、单击即播、方向键连续试听、波形点击定位、区域循环）。后端必须能支撑"连续快速切换文件"这种负载，不是单个文件播一次。
- **任意格式**：WAV、AIFF、FLAC、MP3、OGG Vorbis、M4A/AAC。要覆盖到 cold path，不能靠预转码到统一格式（那会把索引阶段变成转码农场）。
- **可以用 ASIO**。这是本机已有的硬件能力（TOPPING Pro USB Audio Device），被明确允许使用，但要评估可用性代价（见 Q5）。
- **目标形态是常驻服务**：进程起来时打开一次音频流，之后切换文件不再重开设备。

## 核心问题

### Q1（最重要）：常驻流 + 分段喂料，能否让"冷文件第一声"不依赖解码完成？

现在已知：常驻流的发布→出声约 9ms（共享模式，双峰 0–10.5ms）。解码 3 秒 WAV 要 2ms、3 分钟 96k/24bit 要 209ms。

要回答：
- 对一个**从未解码过**的文件，从"决定播它"到"第一批 PCM 进入设备缓冲"，最短路径是什么？
- 是否应该**只解码开头几百毫秒**先出声，其余在播放过程中后台补齐（decode-ahead）？如果是，首段要多少毫秒才够安全（考虑设备回调 10ms 粒度 + 调度抖动）？
- 对超大文件（几十分钟），只解码首段 + 流式后续，是否会让"播放中 seek"变慢？seek 到未解码位置时用户能接受的等待是多少？
- 关键指标：**cold-to-first-sample < 15ms** 是否可达？若不可达，实际下限是多少、由哪一段构成？

需要给出分解预算（决定文件 → 打开 → 探测格式 → 解码首段 → 写入环形缓冲 → 回调取走），每一段都要有实测值。

### Q2：解码线程与音频回调线程如何解耦，才不会互相拖累？

- 环形缓冲（ring buffer）的设计：容量、下溢策略（静音填充 vs 重复上一段 vs 提前预判）、上溢策略。
- 解码在独立线程/线程池，回调只做 memcpy。回调里绝不能有的东西：分配、锁、文件 IO、日志。
- 切换文件时如何做到**无 glitch 切换**：是等旧片段播完、还是立即交叉淡化、还是硬切？Slip Sound 现在的行为是立即停旧播新，听感上是否可接受？
- 参考项目：`rodio`（Rust 音频播放库）的 source/sink 模型是否够用，还是需要自己写调度层？`cpal` 之上有没有必要引入 `fundsp` 之类？

### Q3：输出后端选谁——ASIO / WASAPI 独占 / WASAPI 共享？

**初步倾向：ASIO 为主，WASAPI 共享为回退。** 依据见下（已实测部分）。

> **部分已答（2026-11-16，参考机）**：ASIO 打通了，`TOPPING Pro USB Audio Device` 支持 8–2048 帧的 buffer，`Fixed(64)` 下回调周期 1.45ms、发布→出声中位 **0.68ms**、最差 1.47ms。比 WASAPI 共享（8.33ms）快约 12 倍，且块大小精确无抖动。**设备周期不再是瓶颈。**
>
> **ASIO 多客户端可用**：两个进程同时开 ASIO 流，第二个实例仍 690 callbacks/s、0.69ms，性能无衰减。"开着 DAW 变哑"的担忧在本机不成立（但需在真实 DAW 下复验）。
>
> 仍需回答：
> - 真实 DAW（Ableton/Reaper）占用 ASIO 时 ReSlip 的行为——cpal 双实例不等于 DAW 场景
> - 立体声配置：本轮只协商到 1ch，需确认 2ch 可用性
> - WASAPI 独占模式的对比数据
> - "默认共享、可选 ASIO"的双轨设计是否可行，切换是否要重启流
> - ASIO SDK 的许可证与分发方式（见 Q5）

原计划要测的：
- ~~**ASIO**：用 cpal 的 `asio` feature 打通，测 TOPPING Pro 上的 buffer size / 周期 / 稳定性~~ ✅ 已测，见 `docs/research-notes-playback.md` 第 4 节
- **WASAPI 独占**：`IAudioClient3` + `InitializeSharedAudioStream` 或 exclusive mode，测实际可达周期。
- 对比维度不只是延迟：还有**设备被占用时的行为**（用户开着 DAW，采样管理器还能不能出声？）、切换设备的鲁棒性、多设备并存、蓝牙/USB 热插拔。
- **必须回答**：如果 ASIO 独占会让"DAW 开着时 ReSlip 变哑"，这个方案能不能接受？双轨设计怎么落？

### Q4：索引流程如何做到足够快？

目标不是"比现在快一点"，而是**大库首次索引的时间量级**。Slip Sound 现在对 17 万文件约 2 分钟，主要花在逐文件 `statSync` + 读 64KB 头 + 分类 + 单事务插入。

要调研：
- 并行度：`rayon` 或手写线程池，读文件头是 IO bound 还是 CPU bound？在 NVMe 上的实际并行收益曲线。
- 是否需要读文件头才能拿到 duration/channels/sampleRate？对 WAV/AIFF 可以从头部算出；对 MP3/OGG 可能要做一次快速扫描（但不是全解码）——**最小读取量**是多少？能不能只读前 N KB + 文件尾？
- SQLite 写入：单事务批量插入 vs WAL + 多线程写；索引期间 UI 是否要能查询（需要 WAL）；FTS5 分词在什么时机建立最省时。
- 增量索引：靠 mtime + size 判断变化是否够？目录遍历本身（`readdir` 递归）在 17 万文件上占多少时间？
- **必须给出**：17 万文件的端到端秒数目标，以及各阶段占比。

### Q5：ASIO 的工程代价有多大？

- ASIO SDK 的许可证是否允许随 GPL-3.0 项目分发？（ASIO SDK 是 Steinberg 专有许可，通常要求用户自行下载；这会影响打包流程）
- 没有 ASIO 驱动的用户怎么办？必须有无 ASIO 的回退路径且体验不能崩。
- 是否值得为 ASIO 引入 C++ 构建依赖（`asio-sys` 需要 libclang、MSVC）？还是考虑直接对接 `IAudioClient3` 绕开？
- 跨平台：这个项目要不要只做 Windows？如果要 macOS，CoreAudio 的等价能力是什么（独占模式、buffer 设置）？

### Q6：缓存与内存策略

- 已解码的 PCM 缓存多少？按什么淘汰（LRU / 按目录 / 按当前搜索结果的邻近度）？
- 1 小时 48k 立体声 float32 = 约 1.4GB。不可能全缓存。策略是"缓存最近 N 秒" 还是"缓存最近 N 个文件的完整 PCM"？
- 与 Slip Sound 现有池化预载（4 个元素/邻行）的对应物在原生后端里是什么？答案可能是"预解码邻行的首段"而不是"预建整个元素"。

## 已知的坑

- `asio-sys` 构建：SDK 下载后 `rename` 在 Windows 常失败；手动解压到 `%TEMP%\asio_sdk`。之后还需 `libclang.dll`——**`pip install libclang` 就够**，不用装整套 LLVM（已解决，见调研笔记）。
- cpal 的 ASIO host 常拒绝 `default_output_config()`；要遍历 `supported_output_configs()` 并按 `sample_format()` 分派闭包类型。
- cpal 0.15 在 Windows 上默认走 WASAPI 共享模式，拿不到独占。
- 用虚拟声卡（FxSound / ToDesk / Oculus 之类）测出的数字不代表直连 USB 声卡；参考机的 WASAPI 默认设备是 FxSound，ASIO 才是真正的 TOPPING。务必确认测的是哪条路径。
- Tauri 的 webview 音频与 Electron 同内核同延迟，别在这上面花时间（已实测，见调研笔记第 3 节）。
